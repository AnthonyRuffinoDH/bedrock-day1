Motivation

The Problem

You have an agent in AgentCore. Users in Slack. Tools scattered across environments that AgentCore may or may not be able to reach.

How do you connect all three?

The Old Way

  • LLM-powered thread scraping to reconstruct conversation state
  • Redis to store and expire thread history
  • LLM summarization to compress context into a state store
  • Custom webhook endpoints with public ingress and TLS certs
  • Network gymnastics to route tools through VPCs and firewalls

The Full Picture

Harness

Slack Bridge (Socket Mode)

Connects to Slack via Socket Mode — a WebSocket-based protocol that requires no public endpoint. No ingress rules. No load balancer. No webhook URL rotation.

  • Identifies @-mentions vs ambient channel messages
  • Downloads and base64-encodes image attachments for multimodal payloads
  • Fetches recent thread history to build conversational context
  • Maps threads to deterministic session IDs: slack_{sha256(channel:thread_ts)}
# bot.py — startup
from slack_bolt import App
from slack_bolt.adapter.socket_mode import SocketModeHandler

app = App(token=SLACK_BOT_TOKEN)
handler = SocketModeHandler(app, SLACK_APP_TOKEN)
handler.start()

# Every message → harness → gate or invoke
@app.event("message")
def handle(event, say):
    session_id = make_session_id(
        channel, thread_ts
    )  # sha256 → deterministic
Harness

MCP Tool Proxy

Local MCP tool servers run as Docker Compose sidecars. The harness proxies them to AgentCore over a bidirectional WebSocket.

Agent ↓ {"type": "tool_call", "name": "client__read_file", ...}
Exec ⚡ Harness executes locally via JSON-RPC → mcp-filesystem
Reply ↑ {"type": "tool_result", "content": "...file contents..."}

mcp_tools.json

Declarative config. Auth tokens use ${ENV_VAR} references.

{
  "servers": [
    {
      "name": "github",
      "transport": "http",
      "url": "http://mcp-github:8082/mcp",
      "auth": {
        "type": "bearer",
        "token": "${GITHUB_TOKEN}"
      },
      "tools": [
        {
          "name": "create_pull_request",
          "description": "...",
          "input_schema": { ... }
        }
      ]
    },
    {
      "name": "filesystem",
      "transport": "http",
      "url": "http://mcp-filesystem:8000/mcp",
      "tools": [ ... ]
    }
  ]
}

Supported auth types: bearer, header, basic

Harness

Harness Behaviors

The harness owns the UX layer. The agent never has to deal with rate limits, abuse, or visual feedback.

🚦

Gate Routing

Two-phase processing. Ambient messages go through a gate evaluation sub-agent — classified as RESPOND, IGNORE, or INAPPROPRIATE. Direct @-mentions skip the gate.

⏱️

Throttle & Ban

Per-user rate limiting (default 5s window). Strike-based banning — 3 strikes in 10 min triggers a 60-min ban. All values configurable via env vars.

🔒

Thread Control

Per-thread locking prevents race conditions. Users can @bot silence to permanently mute the bot in a thread.

Emoji Feedback

Visual status via Slack reactions — users see progress without any text output.

🤔Evaluating gate
⏳Generating response
💡Complete
👍Ignoring (ambient chatter)
☝️Inappropriate content
🙈🙉🙊User banned
AgentCore

Unified Tool Surface

The agent sees a single, unified tool surface. Both cloud-side tools and harness-side tools appear together. Namespace prefixes prevent collisions.

PrefixSourceExamples
agent__ Cloud-side (AgentCore) agent__read_file, agent__http_get, agent__channel_memory_store
client__ Harness-side (proxied) client__read_file, client__create_pull_request

Same tool concept, different execution context.
agent__read_file reads the cloud sandbox.
client__read_file reads the harness environment.

AgentCore

Thread State Without LLMs and Redis

Instead of scraping Slack or maintaining a separate state store, Herocore uses two HTTP headers to let AgentCore manage state natively.

Session ID Header

slack_{sha256(channel:thread_ts)}

  • One AgentCore session per Slack thread
  • Agent instance cached in memory, keyed by session ID
  • Thread context injected directly from Slack

User ID Header

x-amzn-bedrock-agentcore-runtime-custom-user-id

  • Maps to channel ID (channel-scoped, not user-scoped)
  • Controls memory namespace:
    /users/{channel_id}/facts
    /summaries/{channel_id}/{session_id}

The Slack thread IS the state

The harness fetches the last N messages (configurable via THREAD_CONTEXT_LIMIT) and injects them as context. No separate state store needed.

Sub-Agents

Sessionless Sub-Agent Flows

The AgentCore layer spawns ephemeral, sessionless sub-agents for focused tasks that shouldn't pollute the main agent's context or tool access.

🚦

Gate Evaluator

Classifies ambient messages as RESPOND / IGNORE / INAPPROPRIATE. No tools, no session. Pure classification with ordered rules.

🧠

Memory Agents

channel_memory_store and channel_memory_recall use dedicated agents with empty tool profiles (preventing recursion) but with a session_manager wired to AgentCore Memory.

🔍

Pre-Recall Agent

On the first message in a new session, checks if stored channel memory is relevant. Returns structured facts or NO_RELEVANT_HISTORY. Avoids polluting conversations with irrelevant historical context.

🌐

Web Extraction Agent

When http_get fetches a page, a nested agent distills raw HTML into content relevant to the current thread. Tool-less, sessionless.

All sub-agents execute, return a result, and are discarded. No cached state, no tool access beyond what they need.

Implementation

An Agent That Can Modify Itself

Docker Compose Orchestration

Three containers. The filesystem server mounts the project root. The GitHub server connects with a PAT. Both expose Streamable HTTP endpoints that the harness proxies to AgentCore. 

services:
  harness:
    build: .
    env_file: .env
    volumes:
      - ./mcp_tools.json:/app/mcp_tools.json:ro

  mcp-filesystem:
    build:
      dockerfile: Dockerfile.mcp-filesystem
    volumes:
      - .:/workspace:ro  # Agent sees its own code

  mcp-github:
    image: ghcr.io/github/github-mcp-server
    command: ["http", "--port", "8082"]
    environment:
      GITHUB_PERSONAL_ACCESS_TOKEN: ${GITHUB_TOKEN}

Vision

A Configurable Bridge Image

It is unclear whether every AgentCore instance will be able to reach into the right environments — your VPC, your internal APIs, your on-prem services.

But you know where your harness is. You know what it can access. And it can connect to AgentCore with OAuth M2M.

The Idea

Ship a single container image configured entirely via environment variables and secrets. No config files mounted. No custom code required.

  • Bridges Slack ↔ AgentCore (WebSocket)
  • Proxies harness-side MCP tools to the agent
  • Handles gate, throttle, ban, emoji, threads
  • Deployers inject auth via env vars + mcp_tools.json

Why proxy instead of direct access?

Rather than punching holes in network boundaries, the harness acts as a bridge.

The harness sits where the tools are

Or where it has network access to reach them.

It authenticates to AgentCore

Via Cognito M2M OAuth (client_credentials grant).

It exposes its local access

To the cloud agent via the WebSocket proxy protocol.

The agent doesn't need to know

Where tools physically run. It calls client__read_file and gets a result. The harness handles routing.

Deployer

Auth Injection

Deployers of Herocore instances are responsible for injecting the right authentication into headers. The mcp_tools.json format supports this natively.

Bearer Token

{
  "auth": {
    "type": "bearer",
    "token": "${MY_TOKEN}"
  }
}

Custom Header

{
  "auth": {
    "type": "header",
    "name": "X-API-Key",
    "value": "${KEY}"
  }
}

The deployer sets the env var. The harness resolves it at runtime.
The agent never sees the raw credential.
